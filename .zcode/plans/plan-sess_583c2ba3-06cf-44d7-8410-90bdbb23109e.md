# 云端生成 34 万字只扣 20 万 token：输入确实可能被漏计

## 结论

**计费公式本身没有故意忽略输入。** 每笔扣的是 `usage.totalTokens`（本意是 prompt + completion）。

**但 chat 流的 usage 解析会把「不完整的 total_tokens」当成最终账单。** 若网关把 `total_tokens` 报成只有输出（或第一帧只有部分用量），输入不会入账。34 万字 → 20 万 token 和这个漏洞对得上。

正常完整模式预估约 **44 万 token**（`estimateWorldGenTokens`，正文 0.7 + 每段 schema/输出 + 检查/成书 × 1.1）。20 万大约是：

- 约 38 个提取单元的 **JSON 输出**（每段情节细纲几乎原文保留，约 5k completion × 38 ≈ 19 万），或
- 全书按 DeepSeek ~0.59 token/字只计 **正文输入**、不含 schema/重叠/输出

两者都远低于「输入 + 输出」。更像 **上游 `total_tokens` ≈ 只含一边**，而代码又 verbatim 拿它去扣费。

---

## 现行数据流

```
LLM SSE (stream_options.include_usage)
  → relaySse() 解析出 TokenUsage
  → callAiJson() 返回 { data, usage }
  → recordTaskUsage() 扣 max(0, round(totalTokens))
  → ai_usage.tokens = 该值；prompt_tokens / completion_tokens 只记账
  → world_gen_tasks.tokens_used += 该值
```

关键代码：

- 扣费：[`server/utils/world-gen-pipeline.ts`](server/utils/world-gen-pipeline.ts) `recordTaskUsage`（约 161–162 行）只认 `usage.totalTokens`
- 解析：[`server/utils/ai-relay.ts`](server/utils/ai-relay.ts) `relaySse` chat 分支（约 222–228 行）

```ts
if (d.usage?.total_tokens && !usageResolved) {
  usageResolved = true  // 第一帧有 total_tokens 就锁死
  usagePromiseResolve({
    promptTokens: d.usage.prompt_tokens ?? 0,
    completionTokens: d.usage.completion_tokens ?? 0,
    totalTokens: d.usage.total_tokens      // 不校验是否 = prompt+completion
  })
}
```

三个问题：

1. **先到先锁**：后面更完整的 usage 丢弃。
2. **没有 `total ?? prompt + completion` 回退**。预生成脚本 [`scripts/prebuild-presets.ts`](scripts/prebuild-presets.ts) 已经这么写了，云端 relay 没有。
3. **不认 `input_tokens` / `output_tokens`**。Anthropic/Responses 路径会加和这两项；世界生成默认 `format: 'chat'`，走不到那里。

`estimateUsage` 缺 usage 时会按 messages + 输出估 **输入+输出**。所以漏计发生在 **有 usage 但 total 偏小**，不是完全没 usage。

次要漏账：`callAiJson` 在流结束后若 JSON 解析失败会抛错，**该次 usage 不入账**再重试。会少扣，但很难单独把一本完成的书压到 20 万。

## 为何 20 万很不正常

提取是每段一次独立调用，**不带前文/世界书**，但每段输入仍有：

- 约 1 万字正文（切段重叠 1000 字，34 万字实际约 **38 段**，不是估算里的 34）
- 约 1k token 的 schema/规则

完整模式粗算：正文输入 ~24 万（0.7）+ schema ~4 万 + 输出 ~8 万 + 检查/成书 → **预检 ~44 万**。即使用更狠的 0.6 tokenizer，输入侧也至少 ~20 万，再加上输出不应停在 20 万。

UI「已入账」直接显示 `task.tokensUsed`，不是字数折算，所以用户看到的 20 万就是实扣。

落地后可用这张账核对某次 `task_id`：

```sql
SELECT SUM(tokens), SUM(prompt_tokens), SUM(completion_tokens)
FROM ai_usage WHERE task_id = ?;
```

- `SUM(completion_tokens) ≈ SUM(tokens)` 且 prompt 很大 → **扣费忽略了输入**（本次最可疑）
- `SUM(prompt_tokens) ≈ SUM(tokens)` → 锁在了第一帧/只计了输入
- 三者都 ~20 万且 prompt+completion ≈ tokens → 公式没问题，是 tokenizer/网关就把总量报成这么少

## 修复

统一 usage 归一化，chat 流改为 **跨分片合并**，扣费用修正后的总量。

### 1. 共享 `normalizeTokenUsage`

新建（建议 [`shared/token-estimate.ts`](shared/token-estimate.ts) 或 `shared/novel.ts` 旁），给 relay / 扣费 / 浏览器中继共用：

- 别名：`prompt_tokens | input_tokens`、`completion_tokens | output_tokens`
- `total = total_tokens || (prompt + completion)`
- 再取 `max(total, prompt + completion)`，避免网关 total 只报一边

### 2. 改 `relaySse` chat 分支（核心）

[`server/utils/ai-relay.ts`](server/utils/ai-relay.ts)：

- 不要 `usageResolved` 第一帧锁定
- 每帧有 usage 就 **按字段取 max 合并**（prompt/completion/total 各自取更大值）
- 流结束：
  - 有合并结果 → `normalizeTokenUsage`
  - 若 `promptTokens === 0` 且已有 messages → 用现成 `estimateMessagesTokens(messages)` 补输入，并加进 total（专门打「网关 total=仅输出」）
  - 完全没有 usage → 维持现在的 `estimateUsage`（输入+输出）

Anthropic/Responses 已是 `prompt + completion`，只改走同一 normalize 即可。

### 3. 扣费兜底

[`recordTaskUsage`](server/utils/world-gen-pipeline.ts) 与 [`chat.post.ts` 流尾结算](server/api/ai/chat.post.ts)：

```ts
const tokens = Math.max(0, Math.round(
  usage.totalTokens || ((usage.promptTokens ?? 0) + (usage.completionTokens ?? 0))
))
```

防止以后再有调用方只填了 prompt/completion。

### 4. 浏览器中继对齐

[`app/utils/aiRelay.ts`](app/utils/aiRelay.ts) 现在是「最后一帧 usage 覆盖」，且 `totalTokens: chunk.usage.total_tokens` 无回退。改成同一套 normalize + 合并，避免本地生成和云端口径再分叉。

### 5. 不回溯已扣账

已完成任务不补扣。修的是后续生成少漏账。若要核对历史，用上面的 `ai_usage` 汇总即可。

---

## 不改的范围

- 预估公式 `estimateWorldGenTokens`（预检宁高勿低，和实扣是两套数）
- 切段/重叠/提取提示词（不是这次少扣的原因）
- JSON 失败丢 usage：可另开，避免重试前那次上游消耗没入账；不是 20 万的主因

---

## 验证

- 单测 `normalizeTokenUsage` + chat 流合并：仅 completion 的 total、仅 prompt 的第一帧、`input_tokens` 别名、后帧更大的 usage
- 用一本短 txt 跑云端生成，看 `ai_usage`：`tokens ≈ prompt + completion`，且 prompt 明显大于 0（提取是大输入小输出）
- 34 万字量级：完整模式实扣应回到预估同量级（约 1.0～1.4 倍字数），不再贴着 0.6× 字数
