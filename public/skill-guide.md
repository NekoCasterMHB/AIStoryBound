# AI StoryBound · Skill 生成指导

> 本指导用于**生成本项目可用的成人玩法 Skill**：说明技能包的文件构造、SKILL.md 格式规范，以及如何合理利用本项目的人物卡/性欲双参数/强度阶梯/嗜好放大等机制，让生成的技能在游戏提示词中准确触发、符合人设、产生预期的情节张力。
> 面向：AI 生成技能、开发者手写技能、审核者检查技能。

---

## 1. 项目技能体系总览

项目将全部玩法技能分为 **3 个大类**，每类一个合集 skill 包。生成新技能前先按判定口诀归类：

| 类 | 判定标准 | 核心底色 |
|---|---|---|
| **小圈**（light） | 管教向、**无性**、强度轻——"过错→责罚→认错→和解"叙事 | 关怀与纠正，情感陪伴 |
| **小圈微大**（light-plus） | 管教底色 + **边缘性行为**（口舌/小型器具/浅插入），无性器官交合 | 管教之上加点"越界" |
| **BDSM**（bdsm） | 性行为 + 深度权力交换 + 高强度/侵入/暴露/囚禁，越界即张力 | 权力与感官的极致 |

**判定口诀**：纯管教无性 → 小圈；有口舌/玩具/手指但不上真身 → 小圈微大；上真身、上强度、上暴露 → BDSM。

**内容边界（硬性约束，写任何技能都不得触碰）**：
1. 不含未成年内容、不含兽交（明确违法项）。
2. 非自愿类仅以"强迫剧本 CNC"形式存在：成人伴侣/主从间**事先约定的征服式剧本**，抗拒、挣扎、哭喊是剧本要素。
3. 其余全部放开：强度、伤害、暴露、囚禁、体液等越界程度均作为剧情张力服务，不设安全红线（但强度档位必须**随人物卡与剧情因素动态选择**，见 §4.3）。

## 2. 技能包文件构造

一个标准技能包 = 一个目录 + 一个构建产物 zip：

```
skills/
  <NN>-<slug>/                    # NN=两位数字序号(01/02/03…), slug=英文短横线名
    SKILL.md                      # ★必带: frontmatter + 正文(注入提示词的核心)
    README.md                     # ★必带(上架硬性要求): 商城说明区展示,不注入提示词
    reference.md                  # 可选: 随附参考文件(注入提示词),术语表/描写词库
    LICENSE.txt                   # 可选: 版权声明(CC BY 4.0)
    <NN>-<slug>-skill.zip         # 构建产物,由脚本生成,不要手改
  shop/
    <slug>.json                   # 可选: 上架配置(name/price/tags/icon/zip 路径)
  README.md                       # 大类总览与判定标准
```

**构建**：`npx tsx scripts/build-skill-zips.mjs`（只处理 `skills/` 下 `^\d{2}-` 开头的目录，把目录内非 zip 文件平铺打包；`shop/`、根 README 不会被误打包）。

**各文件在项目中的角色**（决定内容怎么写）：

| 文件 | 进提示词？ | 用途 |
|---|---|---|
| SKILL.md 正文 | ✅ 注入（示例章节被剥离，见 §4.1） | 指导 AI 怎么展开玩法 |
| reference.md | ✅ 注入（作为"参考文件"块） | 术语、描写词库、节奏建议 |
| README.md | ❌ 不注入 | 商城说明区展示、人阅读的玩法说明 |
| LICENSE.txt | ❌ 不注入 | 版权 |

## 3. SKILL.md 格式规范

### 3.1 frontmatter（YAML）

```yaml
---
name: <英文短横线 slug>        # ★必填,1~60 字符;派生安装 key(见 §5),改动会换 key
description: <中文一句话说明>   # ★必填,解析时截断 200 字;列全本包玩法名
icon: 📏                       # 可选,emoji(≤20 字符),商城卡片展示
tags: [标签1, 标签2, 标签3]     # 可选,数组或逗号分隔;≤6 个,每个 ≤12 字,商城展示
license: CC BY 4.0(LICENSE.txt)
---
```

- `parseSkillMd` 只读 `name`/`description`（缺失报错）；`extractSkillMeta` 读 `icon`/`tags` 供商城卡片。
- `description` 建议格式：`<类名>玩法合集(<玩法名 key>、…)。在<触发情境>时启用;<一句话核心原则>。`

### 3.2 正文结构（建议的章节骨架）

```markdown
# <中文类名> · <副题> <English>

## 何时使用 When to use
- <启用条件 1>(具体、可判定:什么关系/什么情境/什么冲突时启用)
- <启用条件 2>
- 不要用于:<反例>(帮助 AI 排除误触发)

## 叙事原则
1. <该类的叙事铁律:关系铺垫、强度递进、反应层次、收束方式>

## 玩法一:<玩法名> <english-key>
### 触发场景
### 执行步骤(3~6 步,可执行、可检验)
### 强度进阶(低/中/高/极致四档,每档具体到可感知的差异)
### 示例(1~2 个具体场景+展开+收尾)

## 玩法二:…(每个玩法重复)

## 参考文件
- `reference.md`:…
```

**玩法章节命名**：`## 玩法一:训诫 discipline`（序号 + 中文名 + 英文 key，便于 AI 引用和用户识别）。

## 4. 项目机制与技能的交互（写作时如何"利用机制"）

### 4.1 注入与裁剪规则（决定"内容放哪")

- 技能启用后，**SKILL.md 正文 + reference.md 全文**注入 system 规则块（技能总纲："先按各技能的正文指引判断是否适用，适用则按其步骤与规则展开"）——所以**触发判定靠"何时使用"章节**，AI 先看它再决定用不用。
- **示例章节（`### 示例` 标题到下一个标题）在注入时会被 `stripSkillExamples` 剥离**（防止示例的具体场景污染当前小说世界观、省 token）。因此：
  - 可执行指引（触发/步骤/强度进阶/规则）必须写在示例之外，不能依赖示例传递信息；
  - 示例仍要写（供人阅读与商城预览），但只作演示，可放心写"主从同居""师生"等具体设定——不会进提示词。
- 每个技能包**整包注入**（一个包 = 一个注入块），所以：一个包聚焦一个主题（如"打屁股"或"医疗名义"），不要做跨类大杂烩；包的粒度 = 用户在技能管理中开关的粒度。
- README/LICENSE 不注入：README 写给人看（玩法清单、边界说明、触发关键词）。

### 4.2 人物卡机制（技能要"贴卡"）

- 人物卡 kinks **全量注入**（含 `theme·喜欢/厌恶/接受/无感/未知`、`承受/施予/双方`、detail 具体表现），`cardBrief` 会显示"性欲强度档位(数值)"。
- 规则要求：**角色嗜好标注「厌恶」的玩法，日常/奖励场景不主动启用**；但**惩罚场景（犯大错且认错态度差）可故意挑角色「厌恶」的玩法惩罚——越厌恶越显惩罚之重**，并强化抗拒、哭喊、屈辱描写。
- 写作启示：技能的"何时使用"应写成与人物卡可对照的条件（如"角色嗜好含该玩法且非厌恶时作为奖励/自愿玩法；厌恶时仅在惩罚场景作为惩戒手段"），帮助 AI 按卡匹配。

### 4.3 性欲双参数与强度阶梯（核心机制）

项目把"性欲"拆成两个参数：

- **性欲强度**（人物卡静态 0-100）：低值=性冷淡，欲望波动小、难以被挑起。
- **性欲值**（游戏状态动态 0-100）：随心情、情景、被挑逗变化；**低值难上涨、一旦升高后续加速**；戳中嗜好「喜欢」大幅加速（引擎 ×2.5），「厌恶」日常几乎不涨（×0.3），**惩罚场景故意用「厌恶」玩法会因羞耻与服从叠加大幅加速（引擎 ×2.5）**。

**强度阶梯判定**（技能内「强度进阶」档位由 AI 综合选择）：
① 角色性格 ② 性欲强度（静态）③ 当前性欲值（动态）④ 本回合犯错大小 ⑤ 认错态度
——性冷淡/低性欲值用低档；犯错大且认错态度差可跳高档（可故意挑角色厌恶的玩法）；档位变化要有铺垫、逐级推进。

**写作启示**：`强度进阶` 四档不要写成固定套路，每档要写明"什么情况下 AI 该选这档"（如"低档：性欲值低或初识""极致档：性欲值高 + 犯错大 + 嘴硬"），让档位与双参数/剧情因素挂钩；玩法正文可引用性欲值作为推进信号（"性欲值越高，角色越主动/越诚实"）。

### 4.4 内容红线写法

- 高烈度玩法（呼吸控制、电击、滴蜡、体液等）可写极致强度，但**虚构边界**要在"何时使用/不要用于"中写明（如呼吸控制只写"节拍化呼吸/捂口/命令喘息"意象与张力，不写真实窒息过程）。
- CNC 玩法必须写明"成人伴侣/主从间事先约定的剧本"框架。
- 全部玩法延续现有风格：关系铺垫、反应层次（僵直→扭动→讨饶→服软→哭等）、收束留余韵。

## 5. 命名与风格规范

- `name`：英文短横线 slug（如 `light-kink`、`medical-play`）；**安装 key 由 name 派生**（`slugifyKey`：保留字母/数字/中文，其余转连字符，≤64 字符），改名会导致已安装用户 key 变化、需重新导入。
- 玩法英文 key 用短横线（`spanking`、`belt-hands`、`forced-orgasm`），同一包内不重复。
- 语言：中文正文，术语可中英并列（如"训诫 discipline"）；风格与现有 3 个包一致（全角标点、短句、可执行的步骤、具体到可感知的档位描述）。
- `description` 控制在 200 字内（超出截断），列全玩法名便于 AI 识别包内容。

## 6. 构建与上架流程

1. 编写 `skills/<NN>-<slug>/` 下文件（SKILL.md + README.md 必带）；
2. `npx tsx scripts/build-skill-zips.mjs` 生成 zip（脚本自动校验 SKILL.md 可解析）；
3. 上架二选一：
   - **管理员直接上架**：`/admin/skills` →「发布技能」→ 上传 zip → 在线编辑 md → 填售价 → 直接上架（跳过审核）；
   - 普通用户流程：商城「发布」页上传（状态 pending，需管理员审核通过）；
4. （可选）在 `skills/shop/<slug>.json` 写上架配置（name/price/tags/icon/zip 路径），供脚本或人工对照。

**上架校验（发布接口强制）**：zip 可解压、必含 SKILL.md、必含 README（根目录 `README.md` 或 `README`，内容非空）、zip ≤ 1MB、name ≤ 60 字、tags ≤ 6 个且每个 ≤ 12 字。

## 7. 发布前检查清单

- [ ] 目录名符合 `NN-slug`，build 脚本能打包出 zip
- [ ] SKILL.md frontmatter：name/description 必填；icon/tags 可选但建议写（商城展示）
- [ ] 正文含「何时使用」（含"不要用于"反例）与「叙事原则」
- [ ] 每个玩法含：触发场景 / 执行步骤 / 强度进阶(低中高极致) / 示例
- [ ] 核心指引不依赖示例章节（注入时会剥离示例）
- [ ] 强度档位与性欲强度/性欲值/犯错大小/认错态度挂钩，非固定套路
- [ ] 嗜好「厌恶」玩法写明"日常不主动启用；惩罚场景可作为惩戒升级"
- [ ] README.md 存在且内容非空（上架硬性要求）
- [ ] 无未成年内容、无兽交；CNC 带"成人伴侣间约定剧本"框架
- [ ] 玩法 key 不重复、description 列出全部玩法名
