## 1. 需求总览

### 1.1 一句话

**上传一本小说 → AI 自动建世界 → 玩家代入一个角色 → 与 AI 角色互动、选分支、改剧情 → 生成不同于原著的故事。** 设备(含成人设备)仅是可选的外部反馈层,平台核心必须无设备也完整可玩。

### 1.2 核心产品循环

```
上传小说 → 小说解析 → 世界模型构建 → 人物卡生成 → 选角色 → 进入剧情
→ AI 描述场景 → AI 给 3~4 个选项 → 玩家选择/自由输入
→ Game Engine 判断 → 更新状态 → 生成下一剧情 → 触发事件 → 保存记忆 → 继续
```

### 1.3 模块清单(对应规划文档章节)

- 用户系统(§4.1)、TXT 上传与章节解析(§4.2)
- 小说 AI 解析:人物/地点/势力/物品/时间线/世界规则(§5)
- 人物卡(§6)、角色选择与游戏模式(§7)
- AI 扮演:Story AI / Game Master AI / State Engine(§8)
- 对话与选项系统(§9)、Game State(§10)、NPC 独立记忆(§11)、Memory(§12)
- Context Engine(§13)、百万上下文用法(§14)、RAG(§15)
- 剧情分支(§16)、Event System(§17)
- 设备抽象层 / Universal Toy API / 插件体系 / 安全(§18-26)
- AI 结构化输出(§27)、Agent 分工(§28)

### 1.4 十二项技术铁律(所有设计决策必须遵守)

1. LLM 不直接修改数据库
2. LLM 不直接控制设备
3. Game State 必须由程序验证
4. 小说原文与游戏状态分离
5. Memory 与 Chat History 分离
6. NPC 有独立记忆和知识范围
7. 设备通过统一 API 抽象
8. 品牌通过 Plugin 接入
9. 所有外部设备有 Stop / Permission / Limit
10. 百万 Context 用于分析和复杂推演,不每轮回发整本小说
11. 先做 Web 游戏闭环,再做设备
12. 先验证玩法,再扩展插件生态

### 1.5 MVP 分期(规划 §34-37)

- **MVP-1**:TXT 上传 → 章节解析 → 人物提取 → 人物卡 → 选角色 → AI 对话 → 3 选项 → 分支 → 存档。目标:验证"小说 → 可玩 AI RPG"是否好玩。
- **MVP-2**:World Model + NPC Memory + Relationship + Timeline + Game State + RAG。目标:长玩不失忆。
- **MVP-3**:Event Engine + Plugin System + Toy API + 首个 Device Adapter。目标:事件连设备。
- **MVP-4**:Plugin SDK + 角色/剧情/场景市场。目标:从游戏变平台。

### 2.3 关键判断:照搬 vs 自建

**照搬(提示词与交互层)**:PNG 角色卡、Lorebook 注入、深度锚定、滚动摘要、swipe、事件总线、插件 manifest、宏系统。

**必须自建(ST 没有的东西,即本品的壁垒,对应规划 §39)**:

- 确定性 Game State(HP/金钱/flag/关系数值、剧情节点图、条件分支)——ST 完全是软规则,AI 想改就改
- 程序化的事件执行器(LLM 只产 JSON 事件,引擎校验后改状态)
- 小说全文 → 结构化世界模型的解析管线(ST 不做整本小说分析)
- 带时间轴的世界模型与"玩家改变原著"的偏离追踪
- 设备能力协商与安全链

### 3.2 技术栈(最终确定:Cloudflare Workers 全托管,Drizzle 直连 D1,不引入第三方服务)

**部署形态**:Nuxt 4 单应用 → 构建为 Cloudflare Worker(`cloudflare_module` preset,wrangler 部署)。**已移除 @nuxthub/core 与 NuxtHub 的 schema-dts 工具链(该工具链在 Nuxt 4.5.2 / Vite 8 上有兼容问题),改用 Drizzle + 原生 Cloudflare binding,本地环境与生产走同一套 binding 代码,零工具链冲突。**

| 层 | 选型 | 说明 |
|---|---|---|
| 前端+后端 | Nuxt 4.5.2 + Nitro(cloudflare preset) | 一个仓库一个应用,`server/` 即 API |
| 数据库 | Cloudflare D1 + Drizzle ORM | `server/db/schema.ts`,`drizzle-orm/d1` 驱动 |
| 文件存储 | Cloudflare R2 | `server/utils/r2.ts` 访问 `BUCKET` binding |
| 向量检索 | Cloudflare Vectorize(规划,MVP-2 接入) | 小说段落向量 |
| 任务队列 | 按阶段分级:见下 | 不引入 Redis/外部队列 |

**本地开发 = 生产代码(同一套 binding)**:
- 方案:**`nitro-cloudflare-dev` 模块**(官方 C3 集成,底层 getPlatformProxy)+ 根目录 `wrangler.toml` 声明 binding。
- 本地 `pnpm dev` 时,Nitro dev server 里 `event.context.cloudflare.env.DB` / `.BUCKET` 就是模拟的 D1/R2 binding(数据持久化在 `.wrangler/state/v3`)。
- 部署到 Worker 时,Nitro cloudflare preset 提供真实 binding,代码结构完全一致,无需改写。
- 想连云端真实 D1/R2:wranger 配置里 binding 加 `remote = true`(Remote Bindings 已 GA)。

**绑定访问方式**(统一封装在 `server/utils/d1.ts` / `server/utils/r2.ts`):
```ts
// 本地 dev( nitro-cloudflare-dev):  event.context.cloudflare.env.DB
// 部署(cloudflare preset):           env.DB(Nitro 注入,结构一致)
export function getD1Binding(event: H3Event): D1Database {
  const env = (event.context as any).cloudflare?.env
  if (env?.DB) return env.DB
  // 兜底全局
  if ((globalThis as any).__env__?.DB) return (globalThis as any).__env__.DB
  throw createError({ statusCode: 500, statusMessage: 'D1 binding (DB) not available' })
}
export function useD1(event) { return drizzle(getD1Binding(event), { schema }) }
```

**数据库迁移**(不用 NuxtHub 的自建迁移,直接 wrangler):
- Schema:`server/db/schema.ts`(Drizzle sqlite-core,与 D1 兼容)
- 生成:`pnpm db:generate`(`drizzle-kit generate` → `drizzle/*.sql`)
- 应用本地模拟:`pnpm db:migrate:local`(`wrangler d1 execute aistorybound --local --file=...`)
- 应用云端:`pnpm db:migrate:remote`(`wrangler d1 execute aistorybound --remote --file=...`)
- Binding 类型:`npx wrangler types` 生成 `worker-configuration.d.ts`,`server/types.cloudflare.d.ts` 三斜线引用以进入 server tsconfig

**任务队列三级演进(不引入第三方)**:

| 阶段 | 方案 | 实现 | 说明 |
|---|---|---|---|
| MVP-1 起步(当前落地) | **C. 请求内同步处理** | 上传写 R2 → 写 D1 → 解析 → 前端轮询状态 | 零队列概念,最快跑通闭环 |
| 需要并行/超时 | **B. Cloudflare Queues** | 上传 `send()` 一条消息 → 消费 Worker 解析 → 失败自动重试+死信 | 单次解析默认 30s CPU(可配 5 分钟),LLM 等待不计 CPU,够用 |
| 需要可视化进度/断点续跑 | **A.  Cloudflare Workflows** | 多步骤长任务编排,步骤级重试/持久化/可观测 | 小说解析的多步骤(读文件→切章→多轮 LLM→建模型→生成卡)天然匹配 |

> 关键事实:LLM API 调用是网络 I/O 等待,**不计入 Worker 的 CPU 时间**(官方文档明确),所以"等 AI 返回"的时长不消耗配额,重任务的主要成本是内存与请求数,而非 CPU。

## 4. 核心子系统设计

### 4.1 上传与解析管线(规划 §4.2, §5, §28)

```mermaid
流程图(MVP-1 方案 C,同步处理):
上传 TXT → 写 R2(storage_key) → 建 novels 行(status=uploaded)
→ 读 R2、编码检测(UTF-8/GBK/GB18030) → 文本清洗 → 章节识别(正则+LLM 兜底)
→ 切章入库(novel_chapters) → (可选 Queues 消费) Novel Analyzer → 结构化 JSON
→ World Builder(校验/合并) → 生成 characters/locations/factions/items/timelines/world_rules
→ 生成角色卡 PNG(写 R2) → 更新 novels.status=ready → (前端轮询到 ready)
```

要点:
- 超大 TXT 分块读取;编码检测优先(UTF-8 无 BOM 时按 GBK 猜,置信度低可做二次校验)。
- MVP-1(MVP-1.4 之前)解析在请求内同步执行,前端轮询 `GET /api/novels/:id` 拿 `status`;需要并行时再让上传接口 `send()` 入 Queues(方案 B 段落 §3.2)。
- 每个实体保留 `source_chapter` 与 `confidence` 字段,供后续修正与 RAG 溯源。

### 4.2 数据模型(规划 §29 细化,D1/SQLite 方言)

> 说明:以下为 D1(SQLite)方言。D1 列以 TEXT 为主,JSON 形态的字段(游戏状态/关系/flag/etc.)以 JSON 字符串存 TEXT 列,应用层序列化/反序列化;向量数据由 Vectorize 负责(见 4.5),不用建向量列。

```sql
-- 用户
users(id uuid pk, email, password_hash, display_name, created_at)

-- 小说
novels(id uuid pk, user_id fk, title, author, source_format, storage_key,
       encoding, chapter_count, status, parse_progress, world_state jsonb, created_at)
novel_chapters(id uuid pk, novel_id fk, index, title, content text, char_count)

-- 世界模型(带关系/时间线)
characters(id, novel_id fk, name, aliases text[], gender, age, identity,
           personality jsonb, appearance text, background text, abilities text[],
           goals text[], fears text[], secrets text[], first_appearance_chapter,
           death_status, card_image_key, card_json jsonb)
locations(id, novel_id fk, name, type, parent_id, faction_id, description, events text[])
factions(id, novel_id fk, name, leader_id, member_ids uuid[], goals, enemies, friends, resources)
items(id, novel_id fk, name, type, effect, holder_id, origin, importance)
timeline_events(id, novel_id fk, event_index, time_label, location_id,
                participants uuid[], description, preconditions jsonb, aftermath jsonb, chapter)
world_rules(id, novel_id fk, category, content, confidence)

-- 游戏
games(id uuid pk, user_id fk, novel_id fk, player_character_id fk,
      mode, status, save_data jsonb, world_time, started_at, updated_at)
game_states(id uuid pk, game_id fk, player jsonb, relationships jsonb,
            inventory jsonb, quests jsonb, flags jsonb, timeline_position, custom_vars jsonb)
-- 注:game_states 全量快照存储(每次存档写新行),天然支持读档/分支回退(借鉴 S5 的消息快照思路)

-- 记忆
npc_memories(id, game_id fk, npc_id fk, type, content, importance, known_at)
player_memories(id, game_id fk, type, content, importance, chapter)

-- 剧情与事件
scenes(id, game_id fk, scene_id, chapter, location_id, description, dialogue jsonb, prompt_hash)
choices(id, scene_id fk, choice_id, text, risk, required_state jsonb, effects jsonb)
game_events(id, game_id fk, type, payload jsonb, occurred_at, applied boolean)

-- 设备与插件
toy_plugins(id, plugin_id, name, version, manifest jsonb, enabled, installed_at)

-- 向量:段落到 Vectorize 的映射(索引在 Vectorize 侧管理,D1 存元数据)
novel_chunks(id, novel_id fk, chapter_id fk, chunk_index, chunk_text TEXT, vector_id)
```

### 4.3 角色卡系统(借鉴 S3)

- 卡片字段直接采用成熟规范(v2/v3,见 `char-data.js` 的 typedef):`name/description/personality/scenario/first_mes/mes_example/creator_notes/system_prompt/post_history_instructions/alternate_greetings/tags/character_book/extensions`。
- 产品扩展字段(自建,放 `extensions` 命名空间):`role_hp? / role_stats? / relationship_defaults / knowledge_scope`。
- 存储:卡片 JSON 内嵌进 PNG tEXt chunk(`chara`/`ccv3`,base64),头像即卡片;另存 `card_json` 一份便于检索。
- 章节/剧情卡同理:一张"剧情节点图"也可序列化为 JSON 资产,便于市场分享(§37)。

### 4.4 Context Engine(借鉴 S2 + S6)

每次回合的 prompt 按序组装(愿景对齐规划 §13):

```
Priority 0(必保,预占 token):全局系统规则 + 世界规则摘要 + 当前场景
Priority 1:角色卡(description/personality/scenario) + 玩家角色卡
Priority 2(深度锚定注入,doChatInject 思路):
   - 当前目标/任务提示(距末 N 条)
   - 游戏状态相关宏展开({{hp}}/{{money}}/{{location}}/{{chapter}})
   - NPC 记忆片段(atDepth)
   - Lorebook 命中条目(见 4.5)
Priority 3:RAG 检索的小说相关段落(当前人物/地点/事件/章节)
Priority 4:聊天历史(逐条填充至预算耗尽)
Priority 5:滚动摘要记忆(见 4.6)
```

Token 预算:`context_limit - max_output`,`TokenHandler` 先 reserve 必保,再逐条填充历史。

### 4.5 世界观注入 / Lorebook(借鉴 S1)

- 每本小说生成一个 `world_book`(对应 `worlds/<novel>.json`):条目 = 折叠好的小说设定。
- 条目字段(直接采用 ST 成熟结构):`keys, content, constant, selective, insertion_order, position(before/after/atDepth), excludeRecursion, preventRecursion, delayUntilRecursion, probability, group, group_weight, sticky, cooldown, delay, scan_depth, vectorized`。
- 触发源:玩家/NPC 消息文本 + 可选地对角色描述/场景扫描;支持正则关键字;支持 `@@activate`/强制激活事件。
- 用法示例:
  - 地点关键词 → 注入该地点的地理/风土人情报文;
  - 角色名 → 注入该角色隐藏设定(递归可连锁);
  - 神器名 → 1% 概率触发隐藏支线事件。
- 与 RAG 的关系(借鉴 S9):向量检索只**替换关键词检查**,概率/预算/过滤仍走同一套流程;确定性场景优先关键词,开放剧情用向量。

### 4.6 记忆系统(借鉴 S4,对应 §11/§12/§35)

- **总结层**:每 N 条消息或超字数阈值,用单独 summarize 请求把"上次锚点以来的新内容"压成摘要;摘要存为该对话的"锚定系统消息"(`extra.memory` 标记锚点),并同时写入 `player_memories` 表(结构化)。
- **NPC 层(记忆隔离)**:`npc_memories` 每条记录带 `npc_id`,只有该 NPC 在场时注入其记忆;玩家骗过 A,只有 A 记得(§11 的核心卖点)。
- **触发时机**:回合组装时按"当前登场 NPC + 当前场景"筛选注入。
- 编辑/删除消息时同步清理受影响记忆(借鉴 ST 的 `onChatEvent`)。
- 上下文切换(换章/换线)时丢弃未决总结。

### 4.7 Game Engine(自建,本品壁垒)

- 纯 TypeScript 无 IO,输入 `(state, event|choice) → (newState, events[], messages[]|validation)`。
- 规则:
  - 选项 effects 由引擎执行(`relationship.npc_001 += 10`),AI 只产候选场景与建议效果(结构化输出 §27);
  - 每次变更生成 `game_events` 行,`applied=true`,可重放(applied 回滚 = 回档);
  - 状态校验:负数钳制、flag 幂等、时间推进;
  - 条件表达式引擎支持 `relationship >= N`、`flags.has('x')`、`items.includes()` 等(对应 §16 的 conditions)。
- 与 AI 的接口:AI 输出 `{scene, choices[], state_changes[], events[]}` → 引擎校验/执行 → 返回给前端渲染 → 新一轮组装。

### 4.8 设备与插件层(借鉴 S7,对应 §18-26)

- 设备事件由引擎发出(`DeviceEvent{target_device, action, duration, intensity, metadata}`),**AI 永不直连设备**。
- 三层检查:Session 权限 → Capability 检查(`capabilities[deviceId]`)→ 硬限制(max_duration/max_intensity/cooldown/emergency_stop)。
- ToyPlugin 接口按规划 §19 的 `interface ToyPlugin` 实现;插件目录即 `plugins/<brand>/`,manifests 声明 capabilities + permissions。
- 插件安装:git clone + manifest 校验 + 签名可选;加载器注册路由与事件钩子(参考 `plugins.js` + `src/plugin-loader.js`)。
- 近距离监听:**Emergency Stop 永远是最高优先级路径**,断连自动停止。

### 4.9 前端页面(规划 §32/§33 细化)

- 游戏页布局:左=场景描写,中=对话流(打字机流式,参考 `sse-stream.js`),底部=3~4 个选项按钮 + 自由输入框;顶/侧=公开状态面板(角色/地点/时间/HP/金钱/关系/任务)。
- 状态可见性分级:公开(宏可读)/ 隐藏(仅引擎)/ AIInternal(仅进 prompt)。
- Swipe(借鉴 S5):AI 每条回复可重 roll 多条候选、左右滑动切换、书签标记、从书签回退分支 —— 天然支撑"坏结局重选"。
- 交互事件全部走前端事件总线,扩展(设备面板/统计/皮肤)通过 manifest 注册(借鉴 S7)。

## 6. 风险与对策

| 风险 | 对策 |
|---|---|
| 长篇解析成本高、失败率高 | 解析走队列可重试;先生成"可用"再逐步精修;成本上限与配额 |
| AI 生成选项不合逻辑/状态错乱 | 结构化输出 + 引擎强校验 + 回合级回滚(applied 事件可逆) |
| 长上下文成本线性上涨 | 滚动摘要 + Lorebook 按需注入 + RAG,控制每回合 token 预算(S6 强制) |
| 设备安全事故 | 能力协商 + 硬限制 + 双路径 Stop,设备层严禁依赖 LLM 判断 |
| 版权风险(用户上传他人小说) | 上传声明 + 隐私设置 + 私库隔离;PDF 解析需版权策略后再开放 |
| 现金流/成本控制 | 免费层限 parse 次数;结构化解析缓存;批量提示词模板复用 |
