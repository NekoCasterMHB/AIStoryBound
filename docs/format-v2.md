# 作品格式 v2(aisb-book)设计文档

> 状态:v2 单轨(2026-09-05 定稿并全部落地):生成只产 v2、本地强制自动迁移、运行时经 v2ToWork 统一喂 LocalWork;云端端到端验证待部署后执行。详见 §10.0 现状总结 · 本文件是后续各阶段的验收基准
> 关联事故:外部/异版本导出的 `aisb-share v1` zip 中人物卡 `appearance` 为结构化对象、`personality` 为字符串,
> 与当前 `CharacterCard`(appearance:string、personality:string[]) 不兼容,导入后在选角页 `c.appearance?.trim()` 崩溃。
> 结论:**存储/交换层必须"向后容忍、向前可扩",展示层不得假设字段存在且类型正确。**

---

## 1. 背景与动机

### 1.1 问题根因

- 当前人物卡 `CharacterCard` 是**固定类型化 schema**(英文键 + 强类型),生成管线靠"AI prompt 约定"产出,
  但**只在生成边界内强制**;导入 zip / 读取历史数据时**零校验、零归一**,schema 变更也不升分享包版本号。
- 结果:新版/异版产出(结构化外观对象、字符串性格、驼峰字段)进入旧版消费端 → 运行期崩溃。

### 1.2 v2 的目标

1. **向后容忍**:任何来源的人物数据读进来不崩(值形状不苛求,归一化兜底)。
2. **向前可扩**:新版本/作者可自由加属性,旧版本不识别也不炸(自由区 + 动态渲染)。
3. **贴近作者心智**:人物键名用中文、键即文档;人物卡按实际数据动态渲染。
4. **多线叙事自包含**:正文与时序归"正典",每个角色在每段有独立文件承载各自剧情与状态。

## 2. v2 容器规范(aisb-book)

```
书名.book2.zip
├── manifest.json          # 格式标识 + 版本 + 元信息
├── 《书名》.txt           # 小说原文全文(仅归档/阅读用,不被引用不修改,见 §2.1)
├── segments/              # 按段组织:每段一个文件夹
│   ├── 000/
│   │   ├── 正典.json      # 该段细纲 + 正文原文 + 时序/场景(全局真相,唯一真源)
│   │   ├── 何清玲.json    # 该段出场角色:cast 每人一个(本段状态 + 各自剧情/视角/弧线产物)
│   │   ├── 班主任.json
│   │   └── 保安.json
│   └── 001/…
├── characters/            # 跨段不变的基础设定(每人一个文件)
│   ├── 何清玲.json
│   ├── 班主任.json
│   └── …
└── games/                 # 游戏会话(游玩相关所有信息,与作品解耦,见 §5)
    ├── g-xxx/             # 一个会话一个文件夹
    │   ├── session.json   # 会话状态/剧情记录/面板状态/存盘点(GameState + messages + saves)
    │   └── …
    └── …
```

- **正典主干**:每段的 `正典.json` 是正文/细纲/时序的唯一真源,场景里发生的事以它为准。
- **角色分线**:每段 folder 内为**有本段内容**的角色建文件,承载「该角色本段状态」与「该角色各自的剧情/行动线/视角」;
  仅出场、无本段状态的角色**不建文件**,留在 `正典.json` 的 `cast` 里(结构统一且不堆积空壳文件)。
- **正文不按角色拆分** → 无重复膨胀;角色各自剧情不进正文 → 多线/群像叙事自然。
- **游戏会话独立** `games/`:游玩相关信息(会话状态/剧情记录/存盘点)不进作品产物体,一人多局、多角色多局互不影响;支持"分享全部"时打包会话、"仅作品"时不含 games。

### 2.1 归档原文《书名》.txt(仅存档,不参与引用)

- **用途**:小说原文全文的"归档副本"——供阅读器/整本成书/分享阅读;文件名用小说名(如 `<书名>.txt`)。
- **铁律:不被任何逻辑引用、不被修改。** 段内 `正典.json` 的 `text` 才是引擎与 AI 的真相、可编辑源;
  归档全文与段切片**脱钩**,既不用它推导段,也不因段修改而重建(避免"双真源/派生同步"陷阱)。
- 导入时若缺归档全文,可用各段 `text` 按段序拼接生成一次作为初始归档;此后不再维护。

### manifest.json

```jsonc
{
  "format": "aisb-book",          // 固定
  "version": 2,                   // 结构变更必须升版本
  "kind": "book",
  "title": "资料室之行",
  "author": "佚名",                // 可选
  "segmentCount": 12,
  "charCount": 3,
  "tags": ["淡向", "现实"],        // 可选:书架卡/选角页展示用
  "orientation": "不明",           // 可选:性向
  "heat": "淡",                    // 可选:尺度 淡/中/烈
  "setting": "现实校园…",          // 可选:舞台一句话
  "exportedAt": "2026-09-02T08:02:57.792Z"
}
```

> `version` 语义:人物卡契约/分段契约/目录结构任一变化 → 升 version;旧消费者读到 `version > 自己支持` 时提示"请升级"。

## 3. 分段目录契约(已锁定)

### 3.0 分段规则(已定:先粗切 → AI 标剧情转折,段=时间点)

- **parse 后先用 `splitUnits` 按字数/段落边界切成粗段**(≤5.9K tokens,不依赖 AI,可靠)。
- **AI 对已有粗段做"剧情转折/时间点"标注**:为每段判 `转折/时间点标题`(如 相识期/恋爱期/婚后/分手后)、`主角`、`cast`;把属于同一转折的相邻粗段**合并成一个剧情段**。
- 每个**剧情段 = 一个 `segments/NNN/正典.json`**(含段标题、主角、cast、内联 text)。
- 全局时间线:不同段 = 不同时间点,段内每个角色各有该时间点状态(女朋友→老婆→分手,见 §3.2)。
- **AI 不重读全文、不给出字符切点**,只在已有粗段上标转折/合并,省 token 且不易错位。

### 3.1 segments/NNN/正典.json —— 全局真相(细纲 + 原文)

```jsonc
{
  "index": 0,                      // 段序(排序键)
  "title": "恋爱期",               // 时间点/剧情转折标题(可选,如 相识期/恋爱期/婚后/分手后)
  "cast": ["何清玲", "班主任", "保安"],   // 出场人物;值必须与 characters/ 下某文件的「姓名」一致
  "主角": ["何清玲"],               // 可选:本段叙事主角(姓名,可数组;引擎作全局 NPC 锚,未标回退 role==='主角')
  "beat": "细纲:班主任交代任务,何清玲前往资料室…",  // 一句可读细纲(人类浏览用)
  "节点": [                         // ★事件里程碑数组:本段的推进锚/进度锚,AI 标转折时一并生成
    { "n": 0, "事件": "受命送文件至资料室" },
    { "n": 1, "事件": "绊倒散落物品,钥匙落胸前口袋" },
    { "n": 2, "事件": "发现钥匙不见,回办公室认错" },
    { "n": 3, "事件": "去惩戒室核销惩罚通知单" }
  ],
  "place": "办公室、职工区",        // 可选:场景
  "turn": "开端",                  // 可选:起承转合
  "hook": "结尾钩子",              // 可选
  "text": "「报告!」\n\n　　「进。」\n…"    // 本段正文原文(全局真相,只此一份)
}
```

**`节点[]` 语义(已定)**:
- 每段 `beat` 细纲细分为**事件里程碑序列**,由 AI 按剧情自然切分**自主决定个数**(不限制 3~6),按发生顺序排列;事件描述**尽量详细**(保留起因/经过/转折/结果等关键细节,不压缩为短标签),作为段内推进与引导的锚。AI 标剧情转折时与本段一并生成。
- **段内推进度 = 已触发节点数 / 本段节点总数**(AI 每回合报「已达第几个节点」或 0-100%);进度 ≥90%(末节点已触发)即"本段接近尾声",可自然切到下一段。
- **推进/引导锚**:节点是"本段该发生什么"的可选轨道(与玩家行动冲突时以玩家行动为准,同现状豁免);玩家偏离时引擎据下一未触发节点生成引导选项,长期不推进时据此促推。
```

设计取舍(已定):

- **正文内联**:`正典.json` 直接带 `text` 切片,自包含、可独立移动/增删/重排;代价是大长篇全文冗余 2-3 倍,
  `<书名>.txt` 归档全文单独存档、不与段挂钩(见 §2.1)。
- **cast 对齐**:出场人物名必须与 `characters/` 及本段角色文件一致(关联锚),拼写不一致视为该段无此人登场。

### 3.2 segments/NNN/角色名.json —— 该角色的本段状态与剧情(仅建有内容的角色)

```jsonc
// segments/000/何清玲.json
{
  "姓名": "何清玲",                // 关联锚
  "剧情": "受命送文件至资料室;因绊倒散落物品,顺手把钥匙放入胸前口袋;锁门时发现钥匙不见,以为丢失…",  // 该角色本段剧情/行动线/视角,自由文本
  "状态": {                        // 本段状态(浅覆盖 characters/ 基础卡,见 §5)
    "身份": "学生，学习委员",
    "处境": "受老师信任",
    "伤势": "无"
  },
  // —— 自由区:任意键任意值 ——
  "心理": "怕辜负老师的信任",
  "本段关键物": "胸前口袋里的钥匙"
}
```

- 仅出场、无本段可用内容的角色**不建文件**,只出现在 `正典.json` 的 `cast`(是否在某段出场可由 cast 反查)。
- 有可用状态/剧情的角色才建文件:文件含 `姓名` + `状态`(≥1 项)+ 可选 `剧情`。
- **选角/开局按段过滤以文件为准**:按某段开局时,可选角色 = 该段有角色文件的角色;仅出现在 cast 而无文件的角色**不提供选择**(文件即真相)。
- 该文件同时是角色弧线的"段切片":跨段把所有同名文件串起来 = 该角色个人剧情线。
- **"配角故事线"的产物也放这里**:弧线生成/成书阶段为角色产出的事件/行动描述,写进该角色本段文件的 `剧情`
  (或自由区键),即"每个人在这一段都做了什么";引擎与 AI 按段读,不再单独维护一份弧线产物列表。

## 4. characters JSON 契约(已锁定:跨段不变的基础设定)

> **生成时机与职责(已定)**:`characters/` 是 **merge 合并后的跨段不变基础设定**(身份/外貌/性格/背景/目标/关系/数值…),在生成链路的 **merge 阶段之后**由"合并结果 → 中文保留键"的**代码翻译**一次性生成(非 AI 二次汇总)。它承载"所有段共用的基础真相",与段内文件(本段状态/剧情)是"**基础 + 段内浅覆盖**"的互补关系;基础数据唯一不重复,改一处全局生效。若去掉,跨段不变信息只能每段重复或隐式集中首段,一致性/体积/拼卡都变差,故保留。

```jsonc
// characters/何清玲.json
{
  // —— 保留键(中文,AI/作者必须生成;值形状容忍,见 §4.1)——
  "姓名": "何清玲",                 // string,关联锚(cast/关系/游戏状态/文件名)
  "角色": "主角",                   // 结构锚:主角/配角/反派(引擎搭框架用,见 §7)
  "身份": "学生，学习委员",
  "外貌": "高挑,黑色长发…",
  "性格": ["认真", "有责任感"],     // string[] 或 string(容忍)
  "背景": "班主任信任的学习委员…",
  "目标": ["完成老师交代的任务"],
  "关系": [                         // 跨人物引用:对象 = 另一人物「姓名」
    { "对象": "班主任", "值": 75, "说明": "关系较为亲近" }
  ],

  // —— 可选保留键(按需填)——
  "别名": ["学习委员"],
  "性欲强度": 40, "耐心": 60, "心软": 80,   // 数值|null
  "玩法喜好": [{ "主题": "打屁股", "态度": "接受", "角色": "承受", "细节": "…" }],
  "成人属性": { "体位": "…", "习惯": "…" },  // 自由对象
  "首次出场": "第3段",

  // —— 完全自由区(任意键任意值,见 §6)——
  "家庭背景": "单亲,跟母亲生活",
  "癖好细节": "怕痒",
  "口头禅": "好的老师"
}
```

### 4.1 值容忍规则

- **"必须生成"只约束键存在,不约束值形状**。
- 引擎读取统一经「保留键解释器」(§7)做归一:字符串/数组/对象都接受,
  数组→必要时合并为文本、字符串→必要时按 `、，,;；\n` 拆分、`null`/缺失→视为空。

### 4.2 保留键宽度(已定:全语义保留,玩法不回退)

| 保留键 | 类型约定 | 引擎用途 |
|---|---|---|
| 姓名 | string,必填 | 关联锚:cast/关系/游戏状态/弧线 |
| 角色 | 主角/配角/反派 | 结构锚:主叙事视角/徽章(仅 `主角` 有程序分支) |
| 身份/背景/外貌 | string|null | prompt 人物定位 |
| 性格/目标/别名 | string[] 或 string(容忍) | prompt 性格/目标 |
| 关系 | [{对象,值(-100~100),说明?}] | 亲密度 + 正向关系判定 |
| 性欲强度/耐心/心软 | number|null | 数值化行为参数(欲望初始化/脾气/妥协) |
| 玩法喜好 | [{主题,态度?,角色?,细节?}] | 题材玩法注入 |
| 成人属性 | 自由对象 | 成人向属性注入 |
| 首次出场 | string|null | 出场段 |

> 「已死亡」不再是基础卡保留键:死亡是剧情发展到某段才发生的状态,基础卡一律视为生。
> 死亡在**段角色文件**的 `状态` 键里表达(如 `"已死亡": true`,进入该段时临时覆盖,见 §6/§7);
> 旧卡遗留的 `"已死亡"` 键读取时忽略(解释器恒返回未死),再次保存即被清除。局内动态状态的 `dead` 不受影响。

## 5. 游戏会话(已锁定:games/ 独立文件夹)

- **games/ 存放游玩相关所有信息**,与作品产物体(segments/characters/)解耦:
  会话状态、剧情记录(messages)、面板状态(GameState)、存盘点(saves)、玩家身份——一人多局、多角色多局互不影响。
- 一个会话一个文件夹 `games/g-<id>/session.json`,内承载**全部**游玩数据(不拆散到多处)。
- 会话通过 `姓名` 引用 `characters/` 与对应段文件,但不修改它们;同一作品可派生任意多会话。
- **分享语义**:`share|kind=game` 打包 `segments/ + characters/ + games/`(作品 + 游玩);仅分享作品时不带 games/。
- 导入端可只读作品、忽略 games(复盘数据仅供作者/读者看过程)。
- 会话内部格式沿用现有 game JSON 结构(GameState + messages + saves),v2 化仅指"归入 games/ 文件夹、以姓名引用角色"(不重写会话本身)。

## 6. 按段演化(已锁定:状态放分段角色文件)

- **characters/ 只存跨段不变的基础设定**;段内特有状态写在 `segments/NNN/角色名.json` 的 `状态` 里。
- 引擎进入第 N 段时:取该段角色文件 `状态`,与基础卡做**浅覆盖**(值缺失继承基础卡),叠加该角色文件 `剧情` 作为本段该角色分线。
- 替代现 `CharacterCard.chapterVariants` + `effectiveCard` 机制;段与状态同生共死,改段不牵连基础卡。
- 跨段浏览某角色轨迹:按 `characters/姓名` 收集各段同名文件即可汇总(可作为工具能力)。

### 6.1 生成侧产出:提取产出角色剧情 + 弧线按底稿精写(2026-09-05 修订:事实层/叙事层分层)

- **提取阶段(每段)** 直接为每位出场角色产出「本段剧情 + 状态」(**已实施**:extract schema 输出 `plot`):
  - `剧情`(plot) = 该角色本段做了什么(行动线,80~150字),`状态`(status) = 本段处境,均进该段 `角色名.json`;token 预估已随之上调(EXTRACT_OUTPUT 2200→2700,eco 900→1200)。
  - **事实层**:段角色文件的 剧情/状态 是逐段事实的**唯一真源**,全员覆盖(不论登场次数),供分线注入、档案展示与事实对账。
- **配角弧线 = 按底稿精写(修订,原"纯总结"方案否决)**:arcs 请求输入包含该角色各段的 `剧情+状态` 底稿,任务是把客观记录**精化为以该角色为中心的叙事**(逐段 beats 补动机/情绪/目标推进)+ 整线概述与结局——beats 的事实必须与底稿一致。原"纯总结 + 现拼"方案会使扮演配角的逐段戏份质量降级,故否决(详见 §11.1 裁决)。
- **独立 arcs 创建入口已下线(2026-09-09)**:实测弧线步骤是全管线最贵一段(每候选 ≈ 2 万 token,《巴掌印》10 候选 ≈ 20~23 万,≈ 完整生成的一半),单独补跑性价比不足,书架「v1→v2 质量提升补充生成」菜单移除;服务端 `arcs.post.ts` 任务类型与「更新世界情报」写回保留(历史任务仍可写回;完整生成内的 arcs 分支不受影响)。后续若恢复独立入口,先做输入瘦身(只注入登场段±1、缩原文窗口、共享故事线前缀)再放开。
- **职责与权威**:逐段事实 = 段角色文件;整线叙事 = `world.json.characterArcs`(唯一权威,`characters/<名>` 的「弧线」字段已废除)。矛盾裁决:叙事冲突时事实层为准;扮演体验以叙事层为准。
- **处境双写废除(2026-09-09)**:弧线 beat 的 `status`(本段处境变化)停止存储——它与段文件 `状态.处境` 语义重复(两处 AI 各总结一次),且只覆盖弧线候选角色。现状约定:**本段处境唯一真源 = 段文件 `状态.处境`**;弧线 schema/归一化不再产出 status(`CharacterArcBeat.status` 标记废弃,旧数据遗留值由读取端忽略),游玩注入与编辑器在需要处境时当场读段文件。编辑器「分段剧情 / 状态」折叠栏相应收敛为两块:本段独立故事线(纯叙事)+ 本段剧情;处境在「属性状态」行编辑。

### 6.2 生成流程 v2 化(现状 → v2 阶段映射, P4 blueprint)

**现状流程(云端 Workflows,2026-09-06 起 merge 后并行收尾 + 实体消歧)**:
上传 txt → R2 → `parse-plan`(编码/清洗/作者正则/切段) → `author`(AI 提作者,可跳过) → `extract×N`(每粗段 AI 提取: plot_beat + characters[](每个 cast 全套基础字段+status+plot) + 其他实体) → `merge`(合并 entities + 逐字引用校验 + 拼 storyline + 本地聚合;含相邻重叠摘要去重) → **`disambiguate`(实体消歧:名字模式预聚类 → 逐簇 AI 裁决 → 归并别名裂开条目,簇级检查点,全模式)** → `check`(补漏/纠矛盾) → **并行三分支**(成书 `synthesize` ∥ 弧线 `arcs` ∥ 标转折 `annotate`(分块带上一块末段衔接上下文)) → `finalize`(弧线坐标粗段→剧情段换算后 buildBookDoc 落 aisb-book zip)。

**v2 优化点(按段,信息不重复)**:

| 现状 | v2 |
|---|---|
| `splitUnits` 切段后,plot_beat→assembleStoryline→游戏又按 storyline 段,段信息被拆两处 | 切段即产出 `segments/NNN/正典.json`(text=切段原文, beat/cast/place/turn/hook 即 plot_beat),**段即真相,不再重复拼 storyline 数组** |
| 提取时每个 cast 都输出全套基础字段(身份/外貌/性格…),跨段重复 | 提取每段**只输出本段 `剧情`+`状态`**(行动/处境),不再每段重复填全套基础字段;**基础设定靠 merge 合并**(同名跨段 + variants 并列保留 + 冲突清单裁决),省 token、不重复 |
| `synthesize`/finalizeCards 从 entities 拼最终人物卡(英文键) | **`characters/姓名.json` = merge 合并结果翻译成中文保留键结构**,不再是"AI 二次汇总";entities 留作溯源 |
| `arcs` 逐段生成行动摘要(只有登场≥2 有) | 弧线=基于各段 `剧情+状态` 的**跨段纯总结**(见 §6.1),产物入 `characters/<名>.(arc)` |
| 一个大 work 塞 entities/overlay/storyline/characterArcs | 中间产物各有归属:正典(段)/characters(基础)/arcs(总结)/manifest(元数据) |
| 归档全文=finalize 后拼接 | 归档 `<书名>.txt` = 切段前原文,阅读器直接读 |

**最终 v2 生成阶段**:`parse` → `author` → 切段(发出全段文本+归档全文) → 每段产出 `正典.json`(剧情+状态内嵌各角色文件) → `merge` 合并出基础设定 → **翻译成 `characters/姓名.json`(中文保留键,无 AI 二次汇总)** → check → 弧线纯总结(→`characters/<名>.arc`) → 打包落盘(本地 IndexedDB / R2 zip)。

## 7. 动态渲染与编辑规格(已锁定)

### 7.1 选人卡片 / 书架人物卡(展示)

- 保留键 → 富展示:姓名/角色徽章/身份/外貌/性格(标签式)/背景/关系网计数…
- 自由键 → 通用"键:值"渲染:
  - 字符串 → 文本;数组 → 标签/多行;数字 → 数字;布尔 → 是/否;对象 → 子分组缩进
  - 结构化对象(如异版本外貌 `{身高,build,…}`)→ 展开成"键:值"子行,**不崩、可读**
- 折叠:所有字段默认显示 1 行,超长截断省略号;点击展开/收起。

### 7.2 编辑(人物卡编辑器)

- 保留键 → 富控件:文本域(自动增高,默认 1 行)/标签式增删/关系行编辑器/数值滑块或输入框。
- 自由区 → "＋ 添加字段":
  - **键名自由输入**(中文),重复/占用保留键时提示;
  - **值显式选择类型**:文本(单行)/文本(多行)/列表/数字/开关/对象;
  - 已有自由键随时可改键名/类型/删除。
- 外来/未知结构(导入的 zip 里的怪字段)→ 按通用渲染展开,**可编辑不崩**。

### 7.3 开局交互(已定:先选角色 → 再选时间点/段)

- **流程**:开局 = 先选角色 → 再选该角色要切入的**时间点(段)** → 以**该段该角色的身份/状态**开始游戏(如 从"女朋友"期还是"老婆/分手后"期切入)。
- **段 = 时间点**:选段列表展示各段的 `转折/时间点标题` 与主角/剧情摘要;同一角色在不同段身份可不同(女朋友→老婆→分手),玩家选择决定以哪个身份开局。
- 选角/选段均以**文件为准**:可选角色 = 该段有角色文件的角色;无文件不提供(§3.2)。
- 与现有三种开场方式(AI 生成/按细纲段/自定义)关系:选人→选段确定"从哪个身份、哪个时间点开始",其后可继续叠加开场方式(AI 生成开场/自定义背景)细化第一轮。

### 7.4 段推进与引导(已定:节点进度 + 卡住引导)

- **段内进度**:以 `正典.json` 的 `节点[]` 为推进锚。AI 每回合报「已达第几个节点 / 0-100%」;`已触发节点数/总节点数` 即段内进度。≥90% 视为"本段接近尾声",剧情到末节点后可自然切下一段。
- **节点注入范围(已定)**:回合 prompt 只注入「**当前已达节点**摘要 + **下一未触发节点**的详细描述」作为引导锚,其余节点不进每回合 prompt(省上下文又够用)。
- **何时推进**:由**节点进度**驱动,不是回合数;玩家自由度高时进度反映"这段该发生的里程碑已完成多少",玩家行为可把它推到下一段。
- **卡住引导**:段内进度长时间停滞(建议:连续 **5 回合**且进度 <40%)→ AI 生成引导选项,指向**下一未触发节点**("【推进剧情】…"前缀混在当轮 options 中);仍只是建议,自由输入最高优先级。
- 节点是可选轨道:与玩家行动冲突时以玩家行动为准(沿现状豁免),引擎据下一未触发节点提供引导,不强制走主线。

## 11. 风险与开放问题(实施时逐项定)

1. **弧线读取(2026-09-05 修订:world.characterArcs 为唯一权威,「弧线」字段废除,现拼方案否决)**:
   - **分层裁决**:逐段"该角色做了什么/处境如何"的**事实真源 = 段角色文件**(extract 产出的 剧情/状态,全员覆盖);整条弧线的**叙事真源 = world.json.characterArcs**(arcs 任务的一手 AI 产物,角色中心的逐段戏份 + 整线概述 + 结局)——它不是任何其他数据的派生,而是独立生成物,不违反单一真源原则。
   - **arcs 任务按底稿精写(§6.1 分层)**:arcs 请求输入包含该角色各段的 事实底稿(段文件 剧情/状态),beats 的事实必须与底稿一致,arcs 只负责补动机/情绪/目标推进的叙事精化——消除两次独立生成的事实矛盾,叙事质量不降。
   - **「弧线」字段废除**:characters/<名>.json 不再写「弧线」(它曾是 beats 的压缩副本,与 world.characterArcs 构成双份真源,补 arcs 写回时已实际漂移);旧文件遗留的 弧线 键由解释器静默忽略,无需数据迁移。卡片上的弧线展示由读取层从 world.characterArcs 派生。
   - **beatIndex 段号约定(2026-09-08 修订,已修)**:beats 的 `beatIndex` 一律是 **0 起始段下标**(与 `StoryBeat.index` 一致)。提示词里粗段按 `[段1]` 1 基编号、旧文案只说"beatIndex 对应段号",模型据此把 1 基段号直接写进 beatIndex → 弧线整体落到后一段:编辑器里「段N 的本段独立故事线」显示的是段N-1 的内容(与段N-1 段文件的剧情/状态重复),游玩端注入的也是上一段戏份,末段 beat 还被越界丢弃。修复分两层:① 两处弧线提示词显式写明映射([段1] → 0);② `normalizeCharacterArcs` 用该角色登场段集合探测 1 基输出并整体减一(0 基原样通过,登场段缺失时不换算)。**已生成的旧弧线仍是错位的**;独立补生成入口已下线(§6.1),待该入口以瘦身形态恢复后重跑覆盖。
   - **原"读取层现拼"方案否决**:理由:① arc beats 需要 AI 以角色为中心的叙事,主线提取的段剧情视角不同,现拼会把弧线质量降为出场记录;② 存量作品段文件无 剧情,现拼退化。
2. **云端 D1 / 预置 / 工坊(已定:作品与世界产物统一存 R2 zip,不经 D1 列/静态 JSON)**:
